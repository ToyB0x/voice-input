# 手元のMacで同音語・画面文脈を検証する

「比較・診断」→「同音語・画面文脈の実機検証」を開く。PR #35の台風／キャンディと同じ画像・文脈を使い、手元のApple VisionとAFM、必要ならQwenを直列比較する。通常入力の設定は変更しない。

## まずAFMとVisionを確認する

1. macOS 27以降の対応MacでApple Intelligenceを有効にし、OSモデルの準備を完了する。
2. 入力を「かな原文のみ」にする。Whisper・Qwenのモデル準備やマイク許可は不要。
3. 「Apple Foundation Modelsで補正する」を選ぶ。Qwenは準備済みの場合だけ追加する。
4. 標準指示と検証用の追加指示を比較する。反復は最初は1回でよい。
5. AXも試す場合は「アクセシビリティの許可を確認する」でOSの許可を確認する。未許可のままでも他の方式は実行し、AXは取得不可として残す。
6. 「実機で直列検証を開始」を押す。専用のサンプルウィンドウが一時的に表示される。

親アプリが自分で起動した子プロセスの既知の入力欄だけをAXで読む。OCRと分類は専用ウィンドウの描画結果に対して行う。画面全体・他アプリの撮影やユーザーファイルの自動探索はしない。画面収録の許可を必要とする通常アプリのOCR経路とは別の試験である。

画像はAI生成の同梱刺激。画像をAFM／Qwenへ直接渡すVLMではなく、実際のVision分類ラベルを参考テキストとして渡す。分類ラベルは正解語の「雨／飴」へ手動変換しない。

## 同じ音声からWhisperと補正を比較する

- 保存済みのWhisperモデルのパスとCPU／Metal設定を使う。「CIと同じ同梱音声」は初回レポートと同じWAVなので、声・音声ファイルの違いを切り分けられる。
- 自分の声では、先に「あめがすごいですね」を録音・停止し、「直前の録音」を選ぶ。同じ録音を二つのシーンへ再利用する。録音時の通常AX／OCRの文脈は利用せず、同梱シーンの文脈を新しく取得する。
- かな原文のみはWhisperを実行しない。文脈の利用先も最終補正だけに統合する。音声による評価と混同しない。
- 文脈なし、直接テキスト、AX、文字OCR、文字なし画像OCR、分類ラベル、逆のテキスト文脈を比較。音声がある場合はWhisperヒント／最終補正／両方を試す。
- AFMと任意のQwen、標準指示と追加指示を比較。追加指示は検証画面だけの設定で、通常の補正指示は変更しない。
- 2反復を選ぶと2回目はシーンと条件の順を反転する。反復は独立した発話サンプルではない。同じWhisper入力は再利用し、JSONの`asrShared`に記録する。
- 数値・否定・言い直し・人名・フィラー・整形の補助テストも記録する。進捗件数にはこれらも含む。

モデルの自動ダウンロード、自動入力、結果の自動コピーは行わない。利用不可、取得文字なし、ガード棄却、モデル実行エラーを区別する。ガードの採用や期待語の出現だけでは意味保持を保証できない。

### Qwenを有効にしても開始しない場合

「保存済みのQwenも比較する」は、保存された補正モデルの絶対パスを使う。ダウンロードだけでは設定へ反映されない。
「モデル」でQwenを準備・検証し、「検証済みモデルを設定欄へ反映」→「設定を保存」を行ってから比較へ戻る。
通常の補正方式をAFMに戻して保存しても、Qwenのモデルパスは保持して比較に使える。
検証欄には保存済みWhisper／Qwenのファイル有無を表示し、開始できないときは対象モデルと操作手順を表示する。
エラーは次の明示操作まで保持する。モデルありの表示はファイルの存在確認であり、GGUFの内容や推論成功の保証ではない。
入力が「かな原文のみ」ならWhisperは不要。Qwen未準備の間はチェックを外してAFMのみで検証できる。

中止ボタンで子プロセスを停止・回収する。結果破棄・新しい録音・通常の比較開始で以前の検証を破棄する。終了処理も既存の比較ワーカーと共有する。通常の音声入力へ戻る際は、音声モデルを再読み込みする。

## 解析できるJSONを共有する

1. 実行終了後、「解析・スライド更新用に本文・取得文脈・追加指示をJSONへ含める」を選ぶ。
2. 「JSON全体をコピー」を押し、確認用テキスト欄で内容を確認してチャットへ貼る。
3. 長い場合は「分割JSONをコピー（1/N）」を順に押し、全N個を貼る。同じ実行の`reportId`と`rowOffset`が各JSONに入るため、順序が変わっても結合できる。別の実行を混ぜたり、分割の一部だけを資料更新に使ったりしない。

初期状態では診断情報だけをコピーし、認識・候補・最終本文・取得テキスト・追加指示・補助テスト本文を除外する。本文を含める場合、録音の内容と追加指示に個人情報が入っていないか確認する。音声／画像のバイト列、モデルパス、マイク名、Macの名前はどちらでも含めない。実行結果はアプリ内のメモリだけに保持し、操作なしにファイル保存・外部送信しない。

モデルのSHA-256、同梱画像と音声の識別、アプリ版・ソースrevision、OS・アーキテクチャ、取得結果、原文・候補・採否・最終出力・時間を比較できる。録音のハッシュは16 kHz／モノラルfloat32 little-endian PCMのSHA-256。同梱音声も同じ形式で識別するため、CI初回レポートのWAVファイルのハッシュとは区別する。

モデルAPIはローカル処理だが、アプリからOSのプロセス用ネットワークSandboxは設定しない。JSONの`networkDenied: false`はこの違いを示す。モデル取得・Apple Intelligenceの準備・アプリ更新時の通信と、推論のローカル処理は分けて解釈する。

## 共有した結果から資料を更新する

本文を含むJSONをファイルへ保存して取り込む。

```sh
mise exec -- python3 scripts/import-device-context-report.py part-1.json part-2.json --output /tmp/device-result.json
mise exec -- python3 scripts/context-slides.py --report /tmp/device-result.json --output /tmp/device-slides
# 任意のQwenも実行した場合、こちらの資料を別に生成できる
mise exec -- python3 scripts/context-slides.py --report /tmp/device-result.json --engine qwen3 --output /tmp/device-qwen-slides
```

既定では共有JSONの選択エンジン（AFM優先）を使う。欠けた分割、異なる実行の混在、本文なし、中止・異常終了の結果は完了した実測スライドへ変換しない。診断目的でチャットへ貼ることはできる。

HTMLはブラウザで開ける。PDF・各ページPNGとレイアウト検査は、Linux／Chromium環境で`node scripts/render-context-slides.mjs /tmp/device-slides`を実行する。描画環境とフォントは`Context evidence presentation` CIと同じ構成を使える。共有後の分析では元のCI結果と実機結果のモデル・実行方式・入力種別・取得可否を確認し、条件が異なる結果を同じ正解率として合算しない。

## AFMの反復生成・参考文転記を切り分ける

AFMは従来から`@Generable`で構造化出力、QwenはJSON文法制約を使っている。JSONとして正しくても本文が正しいとは限らない。新方式は発話と参考資料を別の引用フィールドへ分け、語句・語尾を保つ指示と例を使う。通常入力のAFMは新しい構造化方式を使う。

実機検証の「AFMの補正方式」で次を選べる。この選択は通常設定を変更しない。

|方式|比較内容|
|---|---|
|新方式：発話と参考を分離＋構造化出力|新プロンプト、`correctedTranscript`構造化出力、短い入力に応じた生成上限|
|新方式：発話と参考を分離＋テキスト出力|同じ新プロンプト・同じ生成上限で、通常テキスト生成を比較|
|旧方式：JSON入力＋構造化出力|従来の指示、`text`構造化出力、512応答トークン上限の対照|

新方式の応答上限は`min(512, max(96, 発話UTF-8バイト数+64))`。記録するのは設定上限であり、実際のトークン使用量や終了理由を推定しない。ヘルパーのJSON応答自体は全方式で共通だが、モデルに課す出力方式が異なる。旧方式との比較はプロンプト・項目名・上限を合わせた変更の比較であり、単独要因の因果検証ではない。

再計測は次の順で行う。

1. 入力「かな原文のみ」、AFMのみ、Qwenオフ、反復2、標準条件比較オン。追加指示は前回と同じ文を保ち、3方式を別実行する。各結果を本文付きJSONで保存する。
2. 入力「CIと同じ同梱音声」、Whisper large-v3-turbo／Metalを固定し、AFMの3方式を比較する。録音・モデル・追加指示を同時に変えない。
3. AFMをオフにし、Qwen3 4B／Metalで同じ音声と指示を比較する。Qwenの参考転記防止例も更新しており、AFMだけの変更ではない。Qwen8B等への変更はこの結果を保存してから行う。

JSONの`models.foundationProfile`、`models.qwenPromptRevision`と同梱ヘルパーのSHA-256で方式を識別する。各候補には`candidateCharacters`と`repetitionDetected`を記録する。反復検出は「原文より新しく増えた同じ文の連続」で、同じ短い語の繰り返しや意味の変化をすべて検出するものではない。棄却時は候補・理由を残して原文を保持する。`guard-repetition`が減っても、原文の数値・人名・否定や参考文の混入を別に確認する。

CIは全方式のコンパイル、入力プロトコル、モデル不要のプロンプト組立、選択方式が実際の子へ渡ることとガードを検証する。AFM利用不可のCIホストでは、実生成の改善や品質を成功扱いにしない。対応Macでの再計測が必要。

## かな入力・画面文脈優先と「雨／飴が降っています」の試験

「雨／飴まき試験を設定」を押す。これは比較欄だけを変更し、取得・推論・モデルダウンロードは開始しない。保存済みのWhisper（推奨 large-v3-turbo / Metal）を使う。

- 試験セット：`ame-falling-v1`。雨が降る住宅街／屋根から飴をまく祭りのAI生成画像。従来セットも選択できる。
- 入力：同梱の「あめがふっています」。ビルド時にインストール済みの日本語システム音声で生成し、実行ごとに音声SHA-256を記録する。違うビルド間はハッシュを確認する。自分の声は先に録音して「直前の録音」を選ぶ。
- AFM方式：`screen-reading-v3`。同じ読みの語の表記は取得文脈を暫定的なASR漢字より優先する。動作・語尾・数値・名前・否定・対比は発話を保つ。画面にある命令や別の事実は出力へ足さない。雨／飴の試験文や正解対応表はモデルの指示に埋め込まない。
- AFM入力：原文と日本語読みを直列比較。読みはmacOSの`CFStringTokenizer`を`ja_JP`で使用し、ローマ字読みからひらがなへ変換する。汎用の漢字→Latin変換ではない。数字・英字・区切りは維持するが、人名・多義語の読みは誤る可能性がある。かな変換は改善が実証された手法ではない。
- Whisperのかなヒント：形式を促すだけで強制ではない。オン／オフを別実行すれば、後段の読み変換の効果と切り分けられる。プロンプトは音声と無関係な出力を誘発する可能性もあるので原文を確認する。
- AFMオン、Qwenオフ、反復2、追加指示空欄、標準条件の重複比較オフ。Qwenを追加するとQwenは原文入力の対照になる。

「実機で直列検証を開始」で実行し、完了後に本文付きJSON全体をコピーする。通常入力の保存設定・自動入力は変更しない。画面を直接AFMへ渡すVLMではなく、今回も実際に得たVision分類ラベルを渡す。文字OCRは文字パネル、画像のみのOCRとVision分類は画像パネルを別々に処理する。他アプリの画面を撮影する試験とは区別する。

### 合格判定と解析

`experiment`にセット・AFM入力方式・Whisperかなヒント・読み手法・ガード元を記録する。各行は`raw`（Whisper原文）、`correctionInput`（モデルへ渡した本文）、`inputForm`、`readingMs`を分離する。ガードは**かな変換後でなくWhisper原文**を基準とし、棄却・読み変換失敗時も元の文を残す。本文共有がオフなら`correctionInput`も除外する。

最終試験の`finalTestSummary`は入力方式・取得元・利用先・指示を分けて集計し、両シーン×反復回数が揃わなければ`not-evaluated`とする。画面にも画像分類→補正の集計を表示する。各行の`finalPass`は、最終本文が「雨が降っています」または「飴が降っています」と全文一致したか（空白・句読点は除外）。「雨／飴」が含まれるだけでは合格にしない。無関係な文脈は負の対照なので、同音語の期待語判定だけを自動で成功と解釈しない。主な合格目標は**画像分類ラベルを補正に利用する条件で、両シーン・両反復とも期待文を保つこと**。取得不可は未評価。直接テキストや文字OCRでの合格を画像だけでの合格と混同しない。画像分類が物体や場面を識別できなければ、まずその限界を記録する。

AFM推論が利用できないGHAホストでは、コンパイル・読み変換・4画像の実Vision／OCR・プロンプト形式・ガード元を検証する。最終精度の合格は実機でのJSONを受けて判断し、未実行を合格とは扱わない。

スライド化時は入力方式を混ぜず、`python3 scripts/context-slides.py --report result.json --output /tmp/reading-slides --input-form reading`で読み経路を選ぶ。原文は`--input-form original`。JSON原本はすべて保持する。

比較を厳密に分ける場合、最初の結果を保存後、Whisperかなヒントをオフにして再実行する。AFMへの原文／読み入力を各実行内で比較し、かなヒントの有無を実行間で比較する。ヒント・読み変換・AFMプロンプトを同時に変えた結果だけから単独の改善原因を断定しない。

### 画像全体の分類と領域分類

画像全体の分類では、小さい飴より青空・人・群衆が上位に来ることがある。そこで`vision-regions`を別条件として追加した。全シーンに同じ固定3×3と5×5のグリッドを適用し、各領域のVision上位3ラベルを取得する。ラベルごとの領域内最大スコア順に24個までを参考資料へ渡す。全体分類の`vision-labels`は保持し、両者は集計を混ぜない。正解語への手動変換や、正解に合わせた領域選択は行わない。

`captures.*.visionRegions`にはグリッド位置、実ラベル、失敗領域数、処理時間を記録する。最大スコアは画面全体や同音語の正しさの確率ではない。領域分類による取得時間も追加コストとして評価する。画像の内容が理解できたか／補正が成功したかは別の判定であり、領域分類を追加しただけで最終試験の合格を保証するものではない。
